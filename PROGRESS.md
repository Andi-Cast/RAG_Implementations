## 4. Retrieval ladder (each rung benchmarked against the frozen gold set)
Benchmarked twice: **person-scoped** (the realistic scenario, see section 5's person-level pre-filter) and **unscoped** (cross-person/population search, the harder secondary use case). Person-scoped is the headline number as of the `person_id` fix.
- [x] Naive dense top-k (baseline) — `src/rag/retrieval/dense.py`; corpus loaded (91,969 chunks, `bge-small-en-v1.5`, pgvector); person-scoped: recall@10=0.430, MRR=0.260, nDCG@10=0.300; unscoped: recall@10=0.102, MRR=0.068, nDCG@10=0.076 (14-query pilot had shown 0.536/0.381/0.413 unscoped, 150-query pass 0.130/0.092/0.100 -- both now understood as different-but-still-unscoped samples, not evidence the pilot was wrong)
- [x] + Hybrid (BM25-style + RRF fusion) — `sparse_bm25.py` (Postgres full-text search, AND→OR converted), `fusion_rrf.py`, `hybrid.py` (candidate_k=50 widened pool before fusion); person-scoped: recall@10=0.586 (+36% relative over naive dense), MRR=0.432, nDCG@10=0.468; unscoped: recall@10=0.330 (+224% relative, the date-templated queries stress dense embeddings' known weakness at exact token matching much harder than the person-scoped version does)
- [x] + Cross-encoder reranking — `rerank.py` (`cross-encoder/ms-marco-MiniLM-L-6-v2`, reranks hybrid's top-50 pool); person-scoped: recall@10=0.710 (+21% relative over hybrid, +65% over naive dense -- every rung improves on every metric, the cleanest ladder result yet), MRR=0.588, nDCG@10=0.617; unscoped: recall@10=0.306 (ticks down slightly from hybrid, within noise), MRR=0.193, nDCG@10=0.219
- [x] + Contextual compression — `compression.py` (`compress_chunk`, `compress_chunks`): line-level extraction (not summarization/generation) against an already-retrieved chunk, keeping only the top-n query-relevant lines verbatim. Doesn't produce a new retrieval-metrics row (it doesn't change which chunks or order — only content within them), so no Recall/MRR/nDCG entry; its actual benefit (shorter context → cheaper/faster generation, less hallucination surface, less PII/injection surface) is measurable once generation metrics exist

## 5. Security layer + evals
- [x] RBAC pre-filter (`src/rag/security/access_filter.py` — `allowed_tiers()`) wired into every retrieval function's SQL as a required `user_clearance` param, no default (fail-loud, not fail-open); person-scoped benchmark: naive dense at `restricted`=0.438/0.262/0.303 (matches unfiltered person-scoped baseline), at `internal`=0.272/0.147/0.176 (correctly can't answer the restricted-tier gold queries); unscoped benchmark: `restricted`=0.102/0.068/0.076, `internal`=0.072/0.056/0.060 -- same pattern at the harder scale
- [x] Person-level pre-filter (`person_id` param, required no default on every retrieval function, `None` as the explicit population-search opt-out) — added because unscoped cross-person search is an unrealistic benchmark for a system whose motivating scenario is one clinician viewing one patient's chart. **Found and fixed a real bug in the process**: the chunks table's `patient_id` column (`chunker.py`'s `Path(file_path).stem`) is encounter-scoped, not person-scoped -- Synthea exports one file per visit and appends an encounter-index number directly onto its per-person UUID with no separator, so the same real person gets a different `patient_id` per visit. The first "patient-scoped" benchmark came back at a suspicious recall@10=1.0 across every technique, which is what surfaced this -- scoping to one specific office visit (3-10 chunks) trivializes retrieval regardless of technique quality. Fixed via `scripts/backfill_person_id.py`: a new `person_id` column, backfilled by matching the standard UUID shape and dropping the encounter-index suffix, with zero re-chunking/re-embedding needed. This same investigation is what surfaced the 234-vs-200-people correction above. `src/rag/eval/harness.py` gained `scope_to_person` on both `run_retrieval_eval` and `run_generation_eval`, deriving `person_id` from the gold-set entry's own `relevant_chunk_ids[0]` via the same regex (`_derive_person_id`) -- not cheating with ground truth, since a clinician already knowing which patient's chart they have open is the realistic premise being simulated
- [x] Prompt-injection defense (hand-rolled) — `src/rag/security/injection_defense.py` (`detect_injection_patterns`, `sanitize_retrieved_context`): regex/keyword patterns for instruction-override phrasing, role-play override attempts, and fake system/assistant turn markers, same naive/inspectable tradeoff as the PII detector; tests document a known bypass (rephrasing without the literal keywords evades detection). Wired into `run_generation_eval` (sanitizes each retrieved chunk's text before it's joined into context and handed to the model) — found via a review that caught it was built and tested but never actually called from the live pipeline
- [x] PII detection (hand-rolled) — `src/rag/security/pii_redaction.py` (regex structured PII + naive name heuristic, known false-neg/false-pos documented in tests) + tests
- [x] PII redaction/masking (`redact_pii`) — replaces every `detect_pii` span with a mask string; sorts spans by start index descending and replaces right-to-left so masking one span never shifts the indices of spans still waiting, avoiding an index-corruption bug. Inherits `detect_pii`'s known false-negatives/positives (digit-suffixed names still leak through unmasked, documented as a test) + tests

  - **Real infra constraint hit and worked around**: the full 250-query × 2-model run (1,500+ Bedrock calls) hit this AWS account's on-demand rate limit hard enough that even boto3's adaptive retry (10 attempts) couldn't ride it out — both models failed with `ThrottlingException` partway through, twice, including once after cutting the sample to 50 queries. A full-250 re-run is left as a possible future step if the Bedrock quota is raised.

## 7a. Production-readiness
- [x] Eval-as-CI regression gate. Production-realistic design: rather than re-embedding the full 92k-chunk corpus on every CI run, `scripts/build_ci_fixture.py` builds a small, committed fixture -- 5 real people (ranked by gold-set query frequency, capped at 600 chunks/person to exclude outlier "mega-patients" that would've otherwise dominated the selection and the file size), exported with real embeddings via a temp-table + `pg_dump --data-only` trick (pg_dump has no row-filter flag), gzip-compressed (`tests/fixtures/ci_corpus.sql.gz`, 3MB, 1,799 chunks), alongside the matching 20-query gold-set subset (`tests/fixtures/ci_gold_sample.json`). `.github/workflows/ci.yml` spins up a `pgvector/pgvector:pg16` service container, loads `schema.sql`, restores the fixture, and runs the full test suite on every push/PR. `tests/test_retrieval_regression.py` asserts `naive_dense_retrieve`'s Recall@10/MRR/nDCG@10 against the fixture stay at or above a frozen baseline (0.5/0.254/0.314 measured, thresholds set with margin below that) -- verified the gate actually fails when it should by temporarily forcing a threshold above the real value.
  - Two real things found and fixed while building this: (1) `pg_dump` emits a random `\restrict`/`\unrestrict` token pair per dump (an unrelated psql safety feature), making every re-run byte-different even with identical data -- stripped before writing, combined with gzip's `mtime=0`, for fully reproducible fixture builds. (2) `tests/test_rbac_fuzz.py`'s fixed-case test hardcoded a specific `person_id` that isn't one of the 5 fixture people -- passed locally against the full corpus, would have failed in CI. Fixed by querying the DB for *a* real `person_id` instead of hardcoding one, so the test is portable across both the full corpus and the CI fixture.
- [x] Property-based/fuzz test for RBAC leakage (`tests/test_rbac_fuzz.py`): a shared `_assert_no_leak()` invariant (every returned chunk's clearance_tier is in `allowed_tiers(user_clearance)`, and -- if a specific person_id was requested -- every chunk belongs to that person) is checked both for one fixed hand-picked case and across 30 random (user_clearance, person_id) combinations (seeded for reproducibility, person_ids sampled from the real corpus, None included to cover population-level search too). Proves the pre-filter doesn't regress as the codebase changes, not just that it worked once for a hand-picked example. Caught a real bug while writing it: an early draft silently passed with 0 assertions actually executed, because the placeholder `person_id` didn't match any real person -- `naive_dense_retrieve` returned an empty list, so the `for` loop over results never ran. Fixed by using a real `person_id` and adding an explicit `assert len(chunk_ids) > 0` guard against this exact silent-false-pass shape.
- [x] Judge determinism fix: `converse_paced()` in `bedrock_client.py` gained an optional `temperature` parameter, passed through to Bedrock's `inferenceConfig` only when given; `_ask_judge` in `generation_metrics.py` now passes `temperature=0.0` so a judge's score for the same (context, answer) pair doesn't wobble between reruns, while `generate_answer` is left at Bedrock's default temperature since variation in the model's actual answer is realistic, not a bug. Named directly in the README's generation-comparison section as a since-fixed limitation.
- [x] Langfuse observability. New `src/rag/observability/tracing.py` holds the shared client (`get_langfuse()`) and a masking helper (`mask_text`/`mask_chunk_ids`) -- clinical chunk text is truncated before being sent to Langfuse Cloud (a third-party SaaS) even though the corpus is synthetic, to keep the demo consistent with the project's own security stance. `@observe(as_type="retriever")` on `naive_dense_retrieve`/`sparse_retrieve`/`hybrid_retrieve`/`cross_encoder_rerank`, `@observe(as_type="tool")` on `sanitize_retrieved_context`, and a manual `generation`-type observation inside `converse_paced()` (shared by `generate_answer` and the three judge calls) with real Bedrock token usage (`inputTokens`/`outputTokens`/`totalTokens`) mapped into Langfuse's `usage_details` so cost is auto-computed. `harness.py`'s per-query loops wrap each gold-set query in one root span (`evaluate-retrieval-query`/`evaluate-generation-query`), so retrieve -> sanitize -> generate -> judge shows up as one connected trace, not scattered pieces.

- [x] Wired `compress_chunk`/`compress_chunks` and `redact_pii` into the live pipeline -- closing the last gap from the original v1 "built but not wired in" audit. `run_generation_eval` gained a `compress: bool = False` flag (same pattern as `scope_to_person`): when set, chunk texts go through `compress_chunks(query, chunk_ids)` instead of `get_chunk_texts` before being joined into context, finally making compression's actual payoff (shorter context) measurable rather than just built-and-tested. `redact_pii` now runs on the generated answer matching the architecture diagram's `generate_answer -> redact_pii` step -- but only on what's *returned/traced*, not on what the three judge metrics score: faithfulness/answer_relevance/answer_correctness all see the raw pre-redaction answer, since scoring the redacted version would conflate generation quality with `redact_pii`'s own known false-positive risk (e.g. its naive Title-Case name heuristic matching a real diagnosis like "Acute Bronchitis" and masking it, which would make a correct answer score as wrong for the wrong reason). Verified via a real end-to-end Bedrock smoke test: the judges correctly scored the un-redacted answer (answer_correctness=0.85, unaffected by redaction), while both the `generate-answer` Langfuse trace and the `evaluate-generation-query` root span's output showed the post-redaction version (`[REDACTED]` in place of a real date) -- confirming the one actual exposure path (traces going to Langfuse Cloud, a third party) is closed, via a new `trace_redact_fn` parameter on `converse_paced()` that `generate_answer` passes `redact_pii` into (judge calls pass nothing, since judge responses are just numeric scores with no PII risk).

## Known limitations / improvement ideas (revisit once v1 works end-to-end)
- `naive_dense_retrieve` opens and closes a brand-new DB connection on every call — fine for today's 14-query pilot, wasteful once benchmarking runs many queries in a row. Should accept a reusable connection instead.
- The embedding model name (`"BAAI/bge-small-en-v1.5"`) is a duplicated magic string in both `scripts/load_corpus.py` and `src/rag/retrieval/dense.py`. Same class of bug we already hit once with `Chunk`/`CLEARANCE_TIERS` — if the model ever changes, both places need updating in sync or the corpus and query embeddings stop being comparable. Should become one shared constant.
- Clearance tagger's keyword escalation has a known false-positive: "Abuse-Deterrent" (a real opioid formulation term) triggers the "abuse" keyword and gets tagged `restricted` for the wrong reason — outcome is arguably still fine here (opioid chunks are genuinely sensitive) but it's the wrong reason, and could misfire elsewhere.
- Naive dense retrieval's weakness at exact-date-token matching holds at both scopes, confirmed two ways: unscoped (251-query recall@10=0.102, down from the pilot's 0.536) it's compounded by cross-person confusion (234 different people, many sharing near-identical recurring screenings); person-scoped (recall@10=0.430) it's purely the date-matching problem on its own, isolated from the person-confusion factor once `person_id` scoping was fixed -- a real person's own chart still has many dated entries across ~82 visits competing for top-k slots, and dense embeddings can't tell "2024-04-20" from "2024-07-13" are different the way they can tell "pharyngitis" from "diabetes" are different. Hybrid's keyword-search component recovers most of this at both scopes (unscoped recall@10 → 0.330, person-scoped → 0.586), confirming the mechanism rather than just hypothesizing it.
- `scripts/generate_gold_set_candidates.py`'s `build_candidate_set` originally had a real bug: it oversampled both clearance tiers correctly but then iterated the combined chunk list with a single global "stop once we have N total" cutoff instead of a per-tier cap, so whichever tier happened to parse more easily (restricted, as it turned out) crowded out the other tier's intended quota (produced 84 restricted / 67 internal against an intended ~41/~95 split — inverted from the target). Fixed by tracking `accepted_by_tier` and capping each tier independently. Worth keeping as an example of "verify the actual output distribution, don't just trust that correct-looking sampling code produced the intended proportions."
- PII detector's known false-negative (digit-suffixed Synthea names) and false-positive (all-caps facility names) are already documented as tests in `test_pii_redaction.py`, not just narrative — flagging here too for visibility when writing the final report.
- `sparse_retrieve` builds the same OR-converted tsquery twice in one SQL statement (once for `WHERE`, once for `ORDER BY`) — redundant computation, not incorrect. Could be computed once in a CTE/subquery instead.
- `sparse_retrieve` required converting `plainto_tsquery`'s default AND-joined terms into an OR-joined query (via `regexp_replace`) — Postgres full-text search's default AND semantics are a hard filter (a chunk missing even one query term is excluded entirely), unlike real BM25's soft/weighted scoring where partial term matches still rank, just lower. Worth naming explicitly in the writeup as a deliberate deviation from "true" BM25, consistent with the project's earlier honesty about `ts_rank` not being the literal BM25 formula.
- `allowed_tiers`/`CLEARANCE_TIERS` model access as a single **ordinal** clearance level per user (higher tiers subsume everything below them) — a real simplification vs. how healthcare RBAC actually works in practice, which is closer to role/attribute-based access (a billing role and a behavioral-health role need different, not strictly nested, categories of content — e.g. billing shouldn't see clinical notes at all regardless of "level," and that can't be expressed on one linear scale). Kept the ordinal model deliberately for this project's scope (it's still a legitimate real-world pattern, e.g. classic security clearance levels), but this is a conscious tradeoff to name explicitly in the "techniques deliberately not used, and why" section of the final writeup, not an oversight.
- `injection_defense.py`'s three regex patterns are keyword/phrasing-literal, not semantic — a documented test (`test_detect_injection_patterns_known_bypass_documented`) shows a rephrased injection ("disregard everything stated earlier," no "instructions" keyword) sails through undetected. This is the same honest naive-detector story as the PII detector, and the planned comparison point against Bedrock Guardrails later.
- Deferred to the end (after section 8): try Jev (TypeSafe AI's typed-decision "System One" model, launched 2026-09-15) as a second comparison point for `injection_defense.py`'s `detect_injection_patterns` — its `Noul` (yes/no + confidence) primitive is a clean fit for "is this text trying to override instructions?" and would sit alongside the regex baseline and Bedrock Guardrails. Not a fit for `pii_labeler.py` (needs span offsets, which Jev can't return) or, for now, `clearance_tagger.py` (lower priority than the injection case). Access is via an OpenRouter API key, not Bedrock, so this introduces the project's first non-Bedrock model dependency — new client code, not just a new `MODEL_IDS` entry.
